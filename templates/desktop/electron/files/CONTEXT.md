# Engineering rules — Electron desktop app

This is a TypeScript Electron app generated by smokeforge. Read this file before
changing code. Read `DESIGN.md` before visual work; the renderer palette has one
source of truth in `src/renderer/src/styles/globals.css`.

## Non-negotiables

- The renderer is untrusted. It must not access Node.js, Electron, filesystem,
  shell, network credentials, or raw IPC.
- `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, and
  `webSecurity: true` are fixed defaults.
- Every renderer-to-main call goes through the typed preload API and the
  `ipc/handle` wrapper. Validate every payload with Zod in main.
- Never expose access tokens, refresh tokens, or secrets to the renderer.
  Tokens live in main-process memory and `safeStorage`.
- Keep services free of Electron imports where possible. Inject dependencies so
  domain logic remains unit-testable.
- Organize code by vertical feature slice, not by generic `handlers/` or
  `utils/` dumps.
- Use `feature:action` request channels and `feature:event` push channels.
- Return the shared `Result<T>` shape across IPC. Do not serialize raw errors.
- Use the `paths` module for userData, logs, temp, and resources. Do not scatter
  string paths.
- Do not put server-like data in Zustand. TanStack Query owns server state;
  Zustand owns local UI state only.
- Settings live in the typed JSON settings store. Durable local app data lives
  in SQLite through Drizzle repositories in the main process. Never store tokens
  or secrets in either; use `safeStorage`.
- Do not run packaging or start long-running processes unless explicitly asked.

## UI component engineering

Use the `frontend-ui-engineering` skill for any renderer component or feature.
Add it with:

```bash
npx skills add https://github.com/addyosmani/agent-skills --skill frontend-ui-engineering
```

Keep components focused: one clear purpose per file, feature code colocated under
`src/renderer/src/features/<feature>`, shared primitives under
`src/renderer/src/components`, and no barrel files. Separate data/container logic
from presentation, avoid prop drilling deeper than three levels, and prefer
composition over configuration. If a file starts handling routing, data access,
forms, and presentation together, split it before adding more behavior. Use the
shadcn CLI for primitives; never hand-write a shadcn component.

## Routing

React Router is the preferred router. Use Data Mode with `createHashRouter` in
`src/renderer/src/app/router.tsx`; hash routing is required for
`app://bundle/index.html`. Keep route objects outside render, use nested routes
for shell layout, route-level error boundaries, and `<Link>`/`<NavLink>` for
internal navigation. Do not introduce another router.

## Quality gate

```bash
make lint
make typecheck
make test
make build
```

A failing command blocks completion. Report actual output; never claim success
without fresh evidence. Use `make package-dir` to inspect the packaged app.
